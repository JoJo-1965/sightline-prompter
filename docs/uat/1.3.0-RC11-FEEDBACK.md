# Feedback queued during 1.3.0 RC11 UAT

12 November 2026. These are reported issues and acceptance requirements for
the next combined candidate, not changes included in the running RC11 build.
Keep the current app, saved settings, script slots and UAT session intact.

## Toolbar utility controls

Status: queued for the next RC.

Joanne reported two forms of the same layout issue:

- On the smaller prompter window, Help and Settings wrap alone onto a second
  row, leaving two orphaned controls and a largely empty toolbar row.
- On a larger window, Help and Settings sit lower than the minimise,
  maximise/restore, fullscreen and Close buttons.

The markup currently gives Help/Settings a normal wrapping flex group, while
the four window controls are absolutely positioned at the top right. Those
different layout rules explain the separation and inconsistent alignment.

### Required result

- Keep Help, Settings and the four window buttons together as one coherent
  utility group at the top right of the first toolbar row.
- Give all six buttons the same vertical alignment, height and spacing.
- Retain the compact script-slot picker on smaller windows and numbered
  buttons on wide windows, including Ctrl+1 through Ctrl+9.
- Let other toolbar functions use coherent additional rows where necessary;
  keep every action visible and accessible.
- Keep session/OBS controls below the complete toolbar, with the existing
  reading-line clearance, auto-hide and keyboard focus behaviour.

### Acceptance for the combined build

Render the actual toolbar at 560, 768, 800, 1024 and 1920 pixels wide, including
the reported narrow and wide states. Check both Voice and Scroll, nine occupied
slots, visible slider values and the OBS/session row. Verify common button
alignment, no orphaned utility controls, clipping or overlap, keyboard access
and auto-hide recovery. Compare the rendered layout as well as element bounds.

Update the cumulative 1.3.0 release notes in the next RC section, affected
screenshots, guide/help and JL preview references with the combined handover.

## Editor Close and Cancel

Status: queued for the same next-RC batch.

The full script editor currently shows Cancel even when the script has no
unsaved changes, including immediately after Save. Joanne requested a dynamic
label so the available exit action is clear.

### Required result

- Show **Close** when there are no unsaved changes; return to the prompter.
- Switch to **Cancel** while there are unsaved edits, retaining the existing
  confirmation before discarding them.
- Return to **Close** only after Save/Save As succeeds, or Undo restores the
  saved text. A failed save or cancelled file dialog must retain the draft and
  the Cancel state.
- Keep Save and Save As available for their existing purposes. Close exits
  the editor rather than closing Sightline.
- Preserve the clear Back to prompter action for read-only sample source and
  its Save a copy route.

### Acceptance for the combined build

Check a clean opened file, a changed file, successful Save, successful Save As,
Undo back to the saved text, a cancelled Save As dialog and failed persistence.
Confirm that cancelling the discard prompt keeps the editor and its draft open;
confirming it returns to the saved script. Include keyboard/screen-reader labels
and the small-window editor toolbar. Update help, screenshots and the next RC's
section of the cumulative release notes with the combined implementation.

## Dialog and Settings window placement

Status: queued for the same next-RC batch.

Joanne requested that a dialog or Settings window first open on its parent's
monitor, then remember its last location when closed and reopen there.

### Required result

- On first use, place each app-owned dialog/utility window on its actual
  parent's monitor, centred within the usable screen area. A dialog opened
  from Settings follows Settings, rather than always following the prompter.
- After the user moves or resizes it, remember its monitor, position and size
  independently for that window type. Reopen at that saved location, including
  after an app restart; moving the parent must not overwrite this preference.
- Persist placement on every supported close route, including the title-bar
  Close button, Escape and the window's own Close/Cancel/Save and close action.
- If the saved monitor has disconnected, fall back to the current parent's
  monitor. Fit the window to the available work area after resolution or DPI
  changes so its title bar and closing controls remain reachable.
- Preserve parent ownership, foreground/focus behaviour, capture protection and
  the existing layout inside each window.
- Parent native operating-system dialogs to the window that opened them.
  Honour placement the OS supports; do not replace native dialogs or claim
  arbitrary positioning where the platform controls it.

### Acceptance for the combined build

Use the operator screen and Elgato prompter as separate monitors. Open Settings
from each screen with no saved placement; then move it, close it and reopen it.
Repeat with a child dialog opened from Settings, Help and another utility
window to check their locations remain independent. Cover restart persistence,
all close routes, a disconnected monitor, changed scaling/resolution and a
fullscreen parent. Verify native dialogs have the correct owner and that no
window reopens off screen or obscures its parent's controls unexpectedly.

## Speakable dialog actions in attention mode

Status: queued for the same next-RC batch.

During background/room and voice checks, Joanne wants to say Continue or Check
again without repeating the wake word: the app is already awaiting her command.
She extended this rule to other dialogs and instruction windows: an enabled
button's visible text should be sayable while attention mode is already active.

### Required result

- Scope contextual voice actions to the active Sightline dialog/instruction
  window while its attention/command session is active. Do not require another
  wake word for each response within that interaction.
- Resolve spoken actions against the window's current visible, enabled buttons
  and labels. Include Continue, Continue anyway, Check again, Close, Cancel and
  the actual next-step labels where those buttons exist. Follow dynamic labels,
  including the queued clean-editor Close / unsaved-editor Cancel change.
- Route the voice action through the same handler as the clicked button,
  retaining prerequisites, confirmation, save-error handling and recording
  permissions. A disabled, hidden or background-window control is unavailable.
- In an audio-check result, Check again repeats the current check rather than
  retaking a script section. Continue follows the existing enabled continuation
  route and retains any explicit acknowledgement of an advisory result.
- Keep ordinary script speech outside these contextual dialogs distinct from
  button commands. Closing the dialog ends its temporary command scope; normal
  wake-word rules resume. An ambiguous label must not activate a guessed action.
- Use the existing visible voice acknowledgement in the active window so the
  operator knows which action was heard. Do not require a separate microphone
  opt-in when the existing enabled command listener is already active.
- Native operating-system dialogs retain their platform behaviour; document
  supported voice behaviour without claiming control Sightline cannot provide.

### Acceptance for the combined build

Exercise actual foreground instruction/dialog windows with Continue, Check
again, Close and Cancel, without another wake word after entering attention
mode. Cover changing labels/stages, disabled controls, nested/background
windows, ambiguous labels, cancellation, errors and returning to normal reading.
Ordinary spoken uses of continue/check again/close outside the contextual
interaction must not trigger a dialog action. Update the contextual help,
button instructions, demos and next RC's cumulative release-note section.

## Speech-triggered voice-check sample

Status: queued with the contextual audio-check controls above.

Joanne requested that the voice-check countdown start when she starts speaking
and finish when she stops speaking, or after ten seconds, whichever comes first.

### Required result

- Arm the voice check and visibly wait for speech; time spent preparing to
  speak must not consume the sample's countdown.
- Start sampling/timing at detected speech onset. Finish on sustained end of
  speech, allowing brief natural breaths, or at a maximum of ten seconds from
  speech onset. Show the correct waiting/measuring/result states.
- Use the measured room/background level to distinguish voice from noise;
  avoid treating a fan or background hiss as speech or demanding higher gain.
- Keep room/background sampling as its own quiet measurement. Speech-triggered
  timing applies to the voice sample rather than its quiet baseline.
- Handle silence/no speech as a waiting or explicitly incomplete check, never
  a successful voice result. Keep retry/cancel available and retain advisory
  handling of a quiet but usable voice sample.
- Exclude the spoken control phrase from the check it starts/retries; allow
  the command to finish before measuring room tone or waiting for test speech.
- Apply consistent behaviour to Prepare to record and script-driven audio
  checks, retaining the automatic meter and visible results in both windows.

### Acceptance for the combined build

Cover a delayed first utterance, a short sentence, natural breathing, sustained
speech beyond ten seconds, silence, quiet speech, steady background noise and
spoken retry/continue. Verify the timer starts on voice rather than window open,
the sample ends on speech completion or the cap, and command phrases do not
contaminate measurements. Pair controlled audio fixtures with Joanne's actual
microphone UAT before marking acoustic behaviour accepted.
